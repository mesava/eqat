# Архитектура EQAT 2.0 / решение до Work

## Контуры
- **Equipment Registry**: поддерживает конфигурации ускорителей и отдельный период их действия, доступность оборудования, энергию/режим, принадлежность фантомов, даты калибровок, факт ремонта.
- **QA Knowledge Base**: тесты + версии SOP + численные критерии + источники/разделы + схемы результатов + варианты измерительного метода.
- **QA Program Builder**: детерминированные правила применимости и требуемые подтверждения, версия черновика, аудит исключений. Никаких автоматически утверждённых требований.
- **QA Execution / QMS**: календарь, фактические исполнения, измерения, review, несоответствия, сервисные события, отчёты; оценить QATrack+ vs свой модуль.
- **Analysis Workers**: Pylinac, PyMedPhys, TRF, iView, XVI, 6DoF, дозиметрия, Agility FullPackage и импорт сторонних измерений; они не управляют ускорителем.
- **File & Provenance**: Orthanc для DICOM в разрешённом сегменте; файловое хранилище с контрольными суммами. Одна первичная серия может обслуживать несколько тестов через отдельные вычисляемые результаты.

## Стек
Локальный сервер: React + TypeScript, FastAPI, PostgreSQL, object/file store, isolated Python analysis workers; по согласованию Orthanc. Защищённый удалённый доступ в будущем через VPN/Zero Trust с MFA, но без прямого внешнего доступа к клиническим хостам.

## Правила генератора
- `present` не равно «тест уже готов»: отдельно хранить наличие фантома, рабочую калибровку, валидацию алгоритма, одобренную SOP/критерий.
- При оценке группы альтернатив достаточно одной `present`. Во всех обязательных группах должны выполняться условия. Достоверно отсутствующая обязательная функция даёт `not_applicable`, неизвестная — `pending_feature_confirmation`, выполненные условия — `eligible_draft`.
- Программа строится по профилю оборудования и клиническим режимам. Протоколы приёмки и эталонные измерения относятся к оценке исполнения и результатам, которые учитываются отдельно.
- Профили ускорителя и КТ разделены. XVI, iViewGT и режимы XVI задаются явно. Порядок заполнения и примеры приведены в [описании генератора](PROGRAM_BUILDER.md).
- Обязательные требования из права/локального регламента никогда не исключать автоматически по удобству.
- Клинические опции (VMAT, SRS, electrons, imaging protocols) проверять дополнительно: наличие энергии не доказывает клиническое применение режима.
- Инструменты могут быть `available`, `missing`, `unverified`, `out_of_calibration`.
- Сервисное событие → review соответствующих post-service QA, без авторазрешения лечения.
- Никаких сетевых подключений к LINAC/MOSAIQ в MVP. iCOM в отдельной исследовательской фазе и только по согласованному пути.

## Контроль версий
`TestDefinition(code)` — стабильный ID; `TestRevision` — методическое содержание; `SOPVersion` — действия; `CriterionVersion` — оценка; `QAProgramVersion` — утверждённый снимок для конкретной установки; `QAExecution` — фактическое выполнение; `qa_dataset` — первичные файлы с хешем; `audit_event` — изменения/подписи.

## Отрицательные сценарии
- Нет baseline → по baseline-зависимому критерию только `NOT_EVALUATED`, не PASS.
- Отсутствует HexaPOD на машине B → `NOT_APPLICABLE`, не просрочка.
- Нет статуса iView/XVI → `PENDING_CONFIRMATION`, не автоматически «имеется».
- Источник изменён → новая версия SOP/criteria, старые отчёты остаются воспроизводимыми.
- Сервисный файл содержит пациентские данные → запрет импорта в публичные репозитории.
